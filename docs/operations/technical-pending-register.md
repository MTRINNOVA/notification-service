# Registro de pendientes técnicos

Registro vivo de pendientes técnicos, deuda conocida y puntos abiertos que **no** resolvieron las decisiones PD-01 a PD-08. **No sustituye a los ADR** ni a [DECISIONS-v1.5.md](../project/DECISIONS-v1.5.md). El historial de PD-01 a PD-08 (todas aprobadas el 2026-11-15) está en [PENDING-DECISIONS.md](../project/PENDING-DECISIONS.md).

Estados: `Abierto`, `Requiere aprobación`, `Planificado (fase N)`, `Cerrado`. Un pendiente solo se cierra con evidencia.

| ID | Pendiente | Impacto | Propuesta | Estado |
|---|---|---|---|---|
| TP-01 | Imágenes Docker no construidas en este entorno (daemon Docker no disponible el 2026-11-15) | Los Dockerfiles de `notification-api`, `notification-worker` y `notification-scheduler` no tienen evidencia de build | Ejecutar `docker build -f src/NotificationService.<Host>/Dockerfile .` para los tres hosts antes de publicar en GHCR | Abierto |
| TP-02 | Base de datos para pruebas de integración de persistencia | Sin ella no se puede validar la Fase 2 contra PostgreSQL real (EF InMemory no está permitido como sustituto) | **Recomendación: Testcontainers** (PostgreSQL efímero por ejecución, igual en local y CI). Alternativas: servicio PostgreSQL en CI o Compose de pruebas | Requiere aprobación (antes de Fase 2) |
| TP-03 | `dotnet-ef` y `Microsoft.EntityFrameworkCore.Design` no instalados | Necesarios para migraciones | Al autorizar la Fase 2: manifiesto local `.config/dotnet-tools.json` con `dotnet-ef` 10.0.x igual a EF Core, y `Design` (con `PrivateAssets=all`) en el proyecto que corresponda | Planificado (Fase 2) |
| TP-04 | Readiness sin comprobaciones de dependencias | `/health/ready` responde *Healthy* porque aún no hay dependencias implementadas | Registrar cada dependencia con la etiqueta `ready` cuando su fase la implemente (PostgreSQL en Fase 2) | Planificado (por fase) |
| TP-05 | Worker y Scheduler sin endpoint/sonda de salud | Docker/Portainer no puede distinguir liveness/readiness de esos procesos | Definir el mecanismo (endpoint HTTP mínimo, archivo de heartbeat o `HEALTHCHECK` del contenedor) al crear el Compose | Requiere aprobación |
| TP-06 | No existe `NotificationService.Scheduler.Tests` | Las pruebas de composición del Scheduler viven temporalmente en `Architecture.Tests` | Crear el proyecto cuando el Scheduler tenga lógica propia (cambio de estructura, requiere autorización) | Requiere aprobación |
| TP-07 | Sin CI/CD | Restore/build/test/vulnerabilidades no se verifican automáticamente | Workflow de GitHub Actions: restore, build Release, test, `--vulnerable`, build de las tres imágenes y publicación en GHCR por tag | Requiere aprobación |
| TP-08 | Sin Docker Compose | Topología solo documentada | Compose de desarrollo y, después, el de producción (Traefik externo, `NOTIFICATIONS_*_HOST`, redes, límites, secretos) en su fase | Planificado |
| TP-09 | Catálogo de códigos de error | **Documentado** el 2026-11-15 en [error-codes.md](../api/error-codes.md) (PD-04). El código aún no lo aplica por completo: `GlobalExceptionMiddleware` emite `code`, `traceId`, `title`, `detail`, `instance` y `status`, pero **no `type`**, que ahora es obligatorio en `ProblemDetails` | Añadir `type` en el middleware y aplicar el catálogo al implementar cada endpoint (no se modificó código en esta tarea) | Abierto |
| TP-10 | Paquetes de pruebas con versiones mayores nuevas disponibles (xunit.runner.visualstudio 4, Microsoft.NET.Test.Sdk 18, coverlet 10) | Ninguno funcional; las versiones actuales funcionan en net10.0 | Evaluar en un cambio dedicado, no "de paso" | Abierto |
| TP-11 | Las imágenes runtime usan el tag `10.0` (flotante dentro de 10.0.x) | Builds no reproducibles byte a byte | Fijar digest en el manifiesto de versiones de release ([docker.md](../deployment/docker.md)) | Abierto |
| TP-12 | `AllowedHosts: "*"` en la API | Sin filtrado de cabecera Host en la aplicación (Traefik enruta por host) | Configurar `AllowedHosts` por entorno a partir de `NOTIFICATIONS_API_HOST`/`NOTIFICATIONS_WEBHOOKS_HOST` cuando existan los DNS reales | Abierto |
| TP-13 | Referencias a documentos inexistentes en el índice (`DECISIONS-2026-11.md`, `CHANGELOG-v1.4.md`) | Navegación documental incompleta | El usuario retiró las referencias del índice | Cerrado |
| TP-14 | El documento OpenAPI generado en tiempo de ejecución (`/openapi/v1.json`) y el contrato normativo (`docs/api/openapi.yaml`) pueden divergir | Riesgo de que el cliente use un contrato no normativo | Al implementar endpoints, añadir pruebas de contrato que comparen lo implementado con `openapi.yaml` | Planificado |
| TP-15 | Alta y gestión de `super_admin` | El ERD define `platform_role_assignments` (PD-01), pero OpenAPI no tiene operación para conceder ni revocar `super_admin`. Tampoco está definido el alta inicial (por eso `granted_by` es nullable) | Definir el procedimiento de alta inicial (tarea operativa controlada y auditada) y decidir si existe una Platform API para conceder/revocar | Requiere aprobación |
| TP-16 | Defectos del contrato OpenAPI no relacionados con PD-01..PD-08 (no corregidos para no cambiar rutas) | (a) Rutas con doble barra: `/management//dashboard/{summary,deliveries,providers-health,consumption}` y `/management//audit/events`. (b) Varias operaciones GET de un recurso individual declaran `page`/`pageSize`. (c) Rutas del inventario ausentes en OpenAPI: `DELETE /management/providers/accounts/{id}`, `DELETE /management/templates/{id}`, `PATCH /management/applications/{id}/status`, `PATCH /management/users/{id}/status`, `PUT /management/roles/{id}/permissions`, `PUT /management/users/{userId}/roles`. (d) `PUT /management/users/{userId}/roles` (inventario) asigna roles al usuario fuera de una membresía, **en contradicción con PD-01** | Revisión de contrato: corregir (a) y (b); incorporar (c) o retirarlas del inventario; para (d), eliminar la ruta o redefinirla (p.ej. como Platform API de `super_admin`, ligada a TP-15) | Requiere aprobación |
| TP-17 | Puerto para prueba de conexión y salud de cuentas de proveedor | OpenAPI expone `testProviderAccount` y `getProviderHealth`, pero los puertos aprobados en PD-03 no indican quién atiende esas operaciones | Añadir una capacidad opcional por canal (p.ej. `IProviderConnectionTester`) o métodos en cada puerto de canal | Requiere aprobación |
| TP-18 | Vínculo notificación–adjunto | El ERD dibuja `NOTIFICATIONS → ATTACHMENTS`, pero `attachments` no tiene `notification_id` ni existe tabla de enlace, aunque `CreateNotificationRequest.attachmentIds[]` admite varios adjuntos | Añadir tabla `notification_attachments (notification_id, attachment_id)` o una columna; decidir antes de las migraciones de adjuntos | Requiere aprobación (antes de Fase 2) |
| TP-19 | Reenvío manual y conciliación | PD-02 exige autorización y auditoría, pero no define si el reenvío crea un nuevo intento o una nueva entrega, si consume cuota, ni el plazo/periodicidad de conciliación por proveedor | Definir al diseñar `retryNotification` y validar los contratos de proveedor | Requiere aprobación |
| TP-20 | Roles personalizados por organización | PD-01 fija los roles v1 (`organization_admin`, `operator`, `viewer`), pero el ERD (`roles.organization_id`) y OpenAPI (`createRole`, `updateRole`) siguen admitiendo roles personalizados por organización. Se conservaron porque PD-01 no los retira | Confirmar si los roles personalizados forman parte de v1; si no, retirar `createRole`/`updateRole` y restringir `roles` a los del sistema | Requiere aprobación (antes de Fase 2) |
